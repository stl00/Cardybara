# Cardybara alpha release

Version metadata lives in release.json. The numeric manifest version is separate from the prerelease label. The release builder packages the standalone wallet, an empty seed of the active banks and locally bundled code. It excludes local data, credentials, personal runtime evidence, source maps and archived ZIPs. ZIP entries have stable ordering/timestamps and per-file checksums.

The standalone build has no ordinary-website bridge content script and no required loopback host access. Bank hosts remain declared; model/loopback hosts are optional. Optional local model requests require the user to configure/consent to that connection. No developer model credentials are provided. The hosted service (`GATEWAY_ORIGIN`, docs/GATEWAY.md) is the default for new users; a package is only useful to beta testers once that gateway is deployed with its provider key set.

## Release flow

1. Pull request → source/history audit → tests/evals → build → package audit → downloadable Actions artifact.
2. Merge main after checks pass.
3. Update release.json and push its matching v-prefixed tag.
4. CI creates a draft prerelease from the exact verified artifact.
5. Unpack that exact ZIP in a fresh Chrome profile. Do not import the owner's backup. Run the acceptance matrix below. A failed/pending item blocks promotion.
6. Chrome Web Store upload/review/publishing is a separate manual process. Store API credentials have not been requested or configured.

## E2E on the packaged extension

The `E2E` CI job runs after `Verify and package` on every pull request and push. It downloads that job's `cardybara-extension` artifact, checks it against `SHA256SUMS`, and runs `scripts/e2e-extension.mjs` on the exact ZIP without rebuilding: install in a clean headless Chrome profile, open the empty wallet, connect Chase, see needs-login, sign in on the synthetic page, let the reading guide read automatically, and check the fields read back while a minimum the page does not show stays unknown. Due dates are billing items rather than record fields and are not covered by this overview read yet. `secure.chase.com` reaches a local HTTPS server that answers with `tests/fixtures/synthetic-bank.html` through Chrome launch options only (`--host-rules`, a certificate pin for a throwaway key); every other host fails to resolve, and the package is not changed. A second step breaks copies of the same package (no service worker, no bank host permission, a worker that does not start, no reading guide, a reader that does nothing) and fails unless each fails for its expected reason. A third step (`--cards`) continues from the main path in the wallet: it adds a card by hand by picking a catalogue product with an anniversary credit, enters a synthetic annual fee date, checks that the credit gets the card-year cycle from that date, edits the card's name and fee date, corrects the name of a card the bank page showed and resets it to the bank's value, then removes the manual card; its negative control enters a fee date that does not exist, so the card is never saved, and must fail. On failure the job uploads `e2e-output` with the log and screenshots of the wallet and the synthetic page. No secrets are used, so fork pull requests run it too.

An extended set runs nightly on `main` (schedule), on manual runs and on every `v*` tag, where the draft release now waits for the whole `E2E` job: after the main path, Chrome is closed and started again on the same profile, and the same extension must come back with its records and the read balance on the wallet, without contacting the bank again (`npm run test:e2e-extended` locally). An extension installed over the debugging pipe lasts for one browser session only, so the harness installs the same unpacked directory again after the restart; Chrome derives an unpacked extension's id from its path, and the test fails unless the id and the profile's extension storage are the same. A control deletes the profile's extension storage while Chrome is closed and must fail. Because the extension is installed again, this exercises `runtime.onInstalled` rather than the `runtime.onStartup` path of an already-registered extension; it does not replace the full browser restart in the exact-artifact acceptance. The set also covers an expired login (`--expired-login`): after the main path, the synthetic bank's sign-in is cleared from every open bank page and the page reloads to its sign-in form, as a timed-out bank session does; the user refreshes Chase from the wallet, the run must stop at needs-login with the earlier records unchanged when it gets there and again just before the sign-in, while the wallet keeps showing the earlier balance; after signing in again the same run must end `updated` with fresh capture times and the same values and show them on the wallet. The test fails if there was no open bank page to expire, and `--restart` and `--expired-login` run separately. A control runs the same check without expiring the session and must fail. The set also covers cancellation (`--cancel`), along the two ways a user stops a reading. First, with the signed-in bank tab closed and the synthetic bank holding its page, the user refreshes all banks and presses 停止本轮刷新 on the wallet while the page is still loading: the run and the Chase job must end `cancelled` with the earlier records unchanged and the earlier balance still shown, and the job must not come back to life once the held page is released and loads. Second, a Chase refresh waits at needs-login (the run is already finished; only the bank page's guide can still read) and the user presses 停止 on the guide: the job must end `cancelled`, the wallet must show it, and signing in afterwards must not read anything or change the records. Two controls each leave out one of the stops and must fail. The set also covers the assistant chat UI with a scripted model (`--chat`): `api.deepseek.com` reaches a scripted synthetic provider on the same local server (by `--host-rules` and the same pinned certificate). The user pastes a made-up test-only key in settings and presses 保存密钥 with real mouse events; headless Chrome cannot answer the extension's host-permission prompt, so the harness first allows the provider host on the extension's details page (Site access: on specific sites, add `api.deepseek.com`, through `chrome://extensions`), which lets the save button's own `permissions.request` resolve without a prompt, and afterwards sets site access back to all sites and checks the bank and provider host permissions. The key must be saved after one key check against the provider, shown masked only, and the chat must show the scripted answer after a `list_cards` tool round; every provider request must carry the saved key, and no balance or card tail read from the synthetic bank may appear in anything sent to the model. The prompt itself is not exercised. Two controls must fail: a key the provider rejects is never saved, and a model that never gives its answer leaves the chat in its error state. The own-key path is developer-only: the harness first sets the `cardybara-dev-own-key` storage flag from the service worker, as a developer would from DevTools. A hosted variant (`--chat --hosted`) leaves the flag unset, checks that settings offer no own key, key field or bank parsing, saves a made-up invite code with 保存邀请码, and the gateway host (`GATEWAY_ORIGIN`) reaches the gateway's own code (`gateway/src/gateway.js` on in-memory bindings), which forwards to the same scripted provider with its own made-up key; every gateway request must carry the invite code and the extension origin, every provider request must come through the gateway with the gateway's key and never the invite code, and the gateway log must carry no body, code or key. Its two controls must fail: a revoked code is never saved, and a code with a daily cap of one cannot finish a two-step chat. The set also covers an upgrade from the previous package (`--upgrade-from <dir>`, `npm run test:e2e-upgrade` locally): `scripts/build-previous-package.sh` builds the newest earlier `v*` release tag from source, or the first parent of the tested commit while no earlier release exists. The main path runs on that previous package; Chrome is closed, the tested package replaces the previous one in the same directory (so the extension id stays the same), and Chrome starts again on the same profile. The extension must then serve the tested package's manifest, wallet page and service worker byte for byte, keep its records and discovered cards, show the read balance and not contact the bank. When the two packages are identical the log says so, and the check only proves the records survive reinstalling. Like the restart check, the reinstall exercises `runtime.onInstalled`; it does not replace the real upgrade in the exact-artifact acceptance. Two controls must fail: extension storage deleted during the upgrade, and a tested package that never replaces a (deliberately different) previous one. `--restart`, `--expired-login`, `--cancel`, `--chat` and `--upgrade-from` run separately.

Locally: `npm run build:release && npm run test:e2e` (Chrome and `openssl` required; `--out <dir>` keeps artefacts, default `.debug/e2e`). The synthetic bank answers at once, which covers the first-load race fixed in stl00/Cardybara#123; `CARDYBARA_E2E_BANK_DELAY_MS=<ms>` adds latency.

`E2E` becomes a required check on `main` once it has been stable, which is a branch-protection change for the owner; #47 stays open until the owner makes it.

## Current public-release blockers

- Real Chrome acceptance of the new empty-wallet onboarding and bank discovery, without an existing owner's backup.
- A standalone AI experience without the developer's local service, with a clear user-owned credential or hosted-account flow.
- Per-bank/product testing beyond the owner's narrow HK Amex and Chase observations.
- Final publisher identity/contact, store listing screenshots, privacy declarations, and reviewer test instructions. Never supply real bank credentials to reviewers.
- Store review has not been performed. CI installs the package in Chrome only against a synthetic bank (below), which is not bank acceptance.

This ZIP is an internal-testing alpha, not a claim that all features, banks, or store requirements are complete. The current cumulative Credit ledger is not a per-voucher redemption ledger. Public eligibility never proves enrollment, usage, reimbursement or a fee waiver.

## Exact-artifact acceptance gate

Create a private pending report with `node scripts/new-acceptance.mjs release/CANDIDATE.zip release/acceptance.private.json`. This command never marks a test passed, and leaves every environment answer and the runtime build empty for the tester to fill in from what they observed. Keep screenshots and actual financial values out of public CI artifacts and Git history.

Required real-Chrome journeys: installation; empty first launch; manual card addition; bank-page discovery; observed field readback; full browser restart with records retained; export/recovery using only the newly created test wallet; cancellation; expired-login recovery; upgrade without lost records. A full browser restart cannot be replaced by reloading a tab. An empty-wallet seed, mocked Chrome APIs or a localhost frontend cannot prove extension installation.

MVP regions: Amex US, Amex HK, Chase, Bank of America, HSBC HK, Standard Chartered HK and Citi US. Amex Canada is archived and not part of acceptance. Citi US stays required, so the gate stays closed until it is really accepted.

For each region, verify every card's balance, statement amount, minimum and payment date against the bank page, plus its Membership Rewards or Ultimate Rewards if it has one, including the actual collection time and executing worker build. An explicit bank statement that a payment is not due may satisfy the minimum and due date, not the balance or statement amount, with its recorded reason. Other rewards programmes are not collected in this version: record `status: "not_collected"` with the programme name and a reason. At Amex the name must be a listed brand, as in the wallet. Neither can stand in for a required programme. Missing data and yearless dates are not completed acceptance: an observed due date records `date` as YYYY-MM-DD and `yearEvidence`, the date text as printed on the bank page, which must contain that year.

Run the frozen held-out assistant eval on a clean checkout of the release tag: `node scripts/eval-holdout.mjs CANDIDATE.zip PRIVATE-REPORT.json`. It refuses local changes, a commit other than the tag's, or a ZIP with another build, and records `heldOutEval` with its source commit in the report; acceptance and promotion check that commit against the tag. The cases are never used for development; see `evals/holdout/README.md`.

`node scripts/acceptance.mjs CANDIDATE.zip PRIVATE-REPORT.json RUNTIME-BUILD` fails closed on a pending case, a held-out assistant eval that did not run on this candidate or fell below its pass rate, old worker, old/mismatched artifact, imported owner backup, developer-service dependency or missing bank acceptance. After it passes, `node scripts/promote-release.mjs CANDIDATE.zip PRIVATE-REPORT.json --publish` reads the expected build from `build-info.js` inside the ZIP rather than the checkout, and additionally compares the GitHub draft asset's SHA-256 before publishing. These checks validate the evidence record; a tester must truthfully observe the real browser and bank results. GitHub owners can bypass local tooling, so the documented review gate remains mandatory.

Billing for every card, and Membership Rewards and Ultimate Rewards, are the required MVP path. AI is optional and must be clearly marked as requiring separate user configuration; it must not block manual setup or rule-based bank collection. Store submission still needs its own review.

## Recovery and data boundaries

Export through the wallet before changing installations; browser origins and extension IDs have separate storage. Keep exports private. No recovery is guaranteed after uninstalling an extension without a backup. Existing local development history is separate from this repository's clean public initial history.
